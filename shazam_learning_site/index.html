第 1 章：音频基础

1.1 音频是什么？

我们听到的声音本质上是空气压力随时间的变化。数字音频就是把这种连续的声波，按固定时间间隔采样成一系列数字。

  • 采样率（Sample Rate）：每秒采多少个点。CD 音质是 44.1kHz，即每秒 44100 个样本。
  • 位深（Bit Depth）：每个样本用多少位表示，决定动态范围。常见 16bit、24bit。
  • 声道（Channel）：单声道、立体声、多声道。

对 Shazam 来说，原始波形包含太多冗余信息。一段 10 秒的 44.1kHz 单声道音频就有 44.1 万个采样点。直接比较波形既不鲁棒也不高效。

1.2 从波形到时频图

人耳感知的是「某个时间有哪些频率在响」，而不是「某一时刻空气压力是多少」。所以 Shazam 先把波形转成时频图（spectrogram）：

  1. 分帧：把音频切成几十毫秒的小段，每段称为一帧。
  2. 加窗：用 Hann 窗等减少帧边界的频谱泄漏。
  3. 傅里叶变换（STFT）：把每帧从时域转到频域，得到该帧内各频率的能量。

一句话：时频图告诉我们「在每一小段时间里，每个频率有多响」。横轴是时间，纵轴是频率，亮度是能量。

1.3 为什么时频图更适合做指纹？

  • 频率信息更稳定：一段旋律的音高、和声结构在时频图上表现为稳定的能量分布。
  • 对时间偏移鲁棒：无论从歌曲哪一秒开始录音，时频结构只要对齐就能匹配。
  • 可降维：不需要保留每个格子的值，只保留最强的那部分峰值即可。

概念检查

  1. 音频数字化依赖采样率和位深
  2. 时频图通过 STFT 把音频表示成「时间 × 频率 × 能量」
  3. Shazam 不把原始波形当特征，而是使用时频图

第 2 章：频谱峰值

2.1 为什么只保留峰值？

时频图仍然是一个很大的矩阵。Shazam 的关键洞察是：只保留局部能量最大的那些点，就足以识别一首歌。

这些峰值就像一首歌的「地标」：

  • 它们是能量最突出的频率成分，不容易被背景噪声淹没
  • 即使录音质量差、有杂音，主要峰值的位置通常保持稳定
  • 峰值数量远小于时频图总格子数，数据量大幅压缩

2.2 如何提取峰值？

找峰值需要两个条件：

  1. 能量阈值：只有能量超过某个阈值的点才可能是峰值。
  2. 局部最大：在时间和频率的邻域内，该点的能量必须比周围所有点都高。
对于时频图中的每个格子 (t, f)：
    如果 energy[t][f] < 阈值：跳过
    如果在邻域内存在 energy[t+dt][f+df] >= energy[t][f]：跳过
    否则：(t, f) 是一个峰值

邻域大小决定了峰值的「稀疏程度」。邻域越大，找到的峰值越少但越稳定；邻域越小，峰值越多但可能包含噪声点。

2.3 峰值的鲁棒性

为什么峰值对噪声鲁棒？想象你在嘈杂的酒吧听歌：

  • 人声、鼓点、贝斯等强能量成分仍然突出
  • 背景闲聊是随机噪声，不会系统性地替代原有强峰
  • 即使少数峰值丢失或新增少量伪峰，整体星座模式仍能被匹配

一句话：峰值是时频图的「骨架」，丢弃软组织后仍能辨认出歌曲的轮廓。

概念检查

  1. 峰值必须同时满足能量阈值和局部最大两个条件
  2. 提高阈值会让峰值数量减少
  3. 峰值对噪声鲁棒，因为噪声不会系统性改变强峰位置

第 3 章：Landmark 指纹

3.1 从峰值到星座图

把一首歌提取出的所有峰值画在「时间-频率」平面上，会得到一张稀疏的点图。因为形状像星空，所以被称为 星座图（constellation map）。

每个峰值点就是一个 landmark（地标），它的坐标是：

  • t：时间帧索引
  • f：频率 bin 索引
  • energy：该点的能量（可选）

3.2 为什么叫「指纹」？

就像人的指纹由独特的纹路组成，每首歌的峰值星座图也有自己独特的时空分布。两首不同的歌，它们的 landmark 分布通常差异很大；同一首歌的不同片段，landmark 分布则高度一致。

3.3 Landmark 指纹的特点

  • 稀疏：一首歌可能只有几千到几万个峰值点，远小于原始音频数据
  • 局部：每个 landmark 只反映一小段时频区域的特征
  • 可组合：多个 landmark 可以组合成哈希，用于快速索引

概念检查

  1. 星座图是峰值在时频平面上的可视化
  2. landmark 由（时间，频率）坐标定义
  3. 不同歌曲的 landmark 分布通常差异明显

第 4 章：哈希与索引

4.1 从峰对到哈希

光有 landmark 集合还不够：如果查询时直接把查询片段的峰值和数据库里每首歌的峰值逐一比对，速度太慢。Shazam 的做法是把局部峰对结构编码成哈希。

具体步骤：

  1. 选一个锚点峰（anchor peak）
  2. 在它附近的固定时间窗口内，找若干目标峰（target peaks）
  3. 对每个目标峰，计算：
hash = (anchorF, targetF, deltaT)
       = 锚点频率 + 目标频率 + 两者时间差

同一个锚点可以在窗口内与多个目标峰组合，因此一首歌的 landmark 能生成大量哈希。

4.2 倒排索引

数据库建库时，把所有歌曲的哈希存入一个倒排索引：

hash_value → [ {songId, time}, {songId, time}, ... ]

查询时，根据查询片段的哈希直接查到数据库中所有可能出现的位置，时间复杂度接近 O(1)。

4.3 哈希设计的 trade-off

参数 太大 太小
目标时间窗口 哈希数量爆炸，索引变大 峰对组合太少，匹配召回率低
峰值阈值 峰值太少，丢失结构 峰值太多，引入噪声
邻域大小 峰值过密，计算量大 峰值过疏，结构信息不足

概念检查

  1. Shazam 哈希通常由锚点频率、目标频率、时间差组成
  2. 一个锚点可以与多个目标峰生成多个哈希
  3. 倒排索引让哈希查找从「扫描全部歌曲」变成「直接定位候选」

第 5 章：匹配原理

5.1 查询片段如何匹配？

当用户用手机录了一段音频，Shazam 也按同样的流程提取峰值、生成哈希。然后把这些查询哈希拿到数据库倒排索引里查。

如果查询片段确实来自某首歌，会发生什么？

  • 查询中的很多哈希，会在数据库里找到相同的哈希值
  • 每个匹配哈希都带有一个数据库时间戳 dbTime 和查询时间戳 qTime
  • 计算时间偏移：offset = dbTime - qTime

5.2 时间偏移投票

关键洞察：如果查询片段来自某首歌的真实片段，那么所有正确匹配的哈希对都应该共享同一个时间偏移。这个偏移就是查询片段在整首歌中的起始位置。

对于每个匹配的哈希：
    offset = dbTime - qTime
    给 (songId, offset) 这个组合投一票

最后统计每个 (songId, offset) 的票数
得票最高的就是最佳匹配

这就像一个「时间对齐」检测：噪声和错误匹配产生的 offset 是随机的，而真实匹配会集中在一个 offset 上，形成明显的峰值。

5.3 为什么从任意位置都能匹配？

用户可能从歌曲开头、中间、副歌任意位置开始录音。无论起始位置在哪，所有正确匹配峰对的 dbTime - qTime 都会整体平移同一个常数。

例如：

  • 如果查询从歌曲第 10 秒开始，offset 就约等于 10 秒
  • 如果从第 30 秒开始，offset 就约等于 30 秒

投票机制会自动发现这个共同的 offset，不需要事先知道查询从哪开始。

概念检查

  1. 匹配时计算 dbTime - qTime 作为时间偏移
  2. 真实匹配的偏移会集中在一个值上，形成直方图峰值
  3. 噪声和错误匹配的偏移是分散的

第 6 章：Shazam 完整流程

6.1 建库流程

原始音频 → 预处理 → 时频图 → 峰值提取 → 峰对哈希 → 倒排索引

6.2 查询流程

用户录音 → 同样预处理 → 提取峰值 → 生成查询哈希 → 倒排检索 → 偏移投票 → 返回结果

6.3 预处理细节

  • 降采样：把 44.1kHz 降到 8kHz 或 11.025kHz，减少计算量同时保留人声和主要乐器信息
  • 分帧：通常 32ms 一帧，帧移 50%
  • 加 Hann 窗：减少频谱泄漏
  • STFT：得到时频表示

6.4 为什么查询和建库必须用同一套参数？

只有完全相同的预处理、峰值提取和哈希参数，才能保证同一首歌曲在数据库和查询时生成可对齐的指纹。如果参数不同，同一个物理时间点可能对应不同的帧索引，匹配就失效了。

一句话：Shazam = 同一套指纹算法 + 倒排索引 + 时间偏移投票。

概念检查

  1. 建库和查询使用完全相同的指纹提取流程
  2. 预处理包括降采样、分帧、加窗、STFT
  3. 最终匹配依赖时间偏移投票直方图

第 7 章：优缺点与边界

7.1 Landmark 指纹的优势

  • 计算轻量：峰值提取和哈希计算都很简单，适合移动端和实时识别
  • 索引紧凑：倒排索引只存哈希到（歌曲，时间）的映射
  • 对噪声鲁棒：随机噪声不会系统性地改变强峰位置
  • 对压缩/失真鲁棒：MP3、AAC 压缩主要损失弱能量细节，强峰基本保留
  • 无需训练：不需要神经网络或大量标注数据

7.2 Landmark 指纹的局限

  • 对翻唱/变奏弱：不同歌手演唱、乐器改编会改变频谱结构
  • 对变速/变调敏感：时间拉伸和音高改变会破坏峰对的时间差和频率
  • 对极端噪声敏感：如果噪声完全淹没音乐，峰值结构会被破坏
  • 只匹配录音：对哼唱识别效果差

7.3 与神经网络方法的对比

维度 Landmark 指纹 神经网络嵌入
特征来源 handcrafted 时频峰值 数据驱动学习的高层语义嵌入
是否需要训练 不需要 需要大量数据和算力
对原录音 非常强 强
对翻唱/变奏 弱 可训练得更强
可解释性 高，峰值和哈希都可视 低，嵌入向量难直接解释
计算成本 低 高（推理+索引）

7.4 什么时候选 Landmark，什么时候选神经网络？

  • 选 Landmark：需要快速、轻量、可解释、对同一录音识别的场景，如听歌识曲、广告监测、版权保护
  • 选神经网络：需要理解旋律、风格、翻唱关系，如哼唱识别、cover song 检测、音乐推荐

一句话：Landmark 是「精确匹配录音」的专家；神经网络是「理解音乐语义」的通才。实际系统可以两者结合。

概念检查

  1. Landmark 对原录音、噪声、压缩鲁棒
  2. Landmark 对翻唱、变速、变调相对脆弱
  3. 神经网络嵌入更适合语义层面的音乐理解

总结与延伸

Shazam 完整流程

录音/音频 → 预处理 → 时频图 → 峰值/星座图 → 峰对哈希 → 倒排索引 → 时间投票匹配
1️⃣预处理

降采样、分帧、加窗、STFT，把波形变成时频图。

2️⃣峰值提取

保留局部能量最大点，形成稀疏的星座图 landmark。

3️⃣组合哈希

用锚点-目标峰对生成（频率，频率，时间差）哈希。

4️⃣倒排索引

把哈希映射到（歌曲ID，时间戳），实现快速检索。

5️⃣时间偏移投票

对匹配哈希计算 dbTime - qTime，统计直方图峰值得到最佳匹配。

核心要点回顾

1. 时频图

把音频从「时间-振幅」变成「时间-频率-能量」，是提取指纹的基础。

2. 峰值与哈希

只保留强峰，用峰对组合成紧凑哈希，大幅压缩数据并保留可匹配结构。

3. 偏移投票

通过时间偏移直方图，把「像不像」变成可统计的票数问题。

延伸学习路径

  • 信号处理：STFT、CQT、梅尔频谱、 Hann 窗与频谱泄漏
  • 音频指纹论文：Shazam 原始论文《An Industrial-Strength Audio Search Algorithm》
  • 神经网络音频识别：MusicNN、CoverHunter、ByteCover 等基于学习的方案
  • 工程实践：大规模倒排索引、实时音频流处理、移动端推理优化

一句话总结：Shazam 把「听音识曲」这个直觉问题，变成了一套可工程化、可扩展的指纹提取 + 哈希索引 + 时间投票流程。
