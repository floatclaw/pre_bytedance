第 1 章：向量与 Embedding

1.1 为什么需要向量数据库？

传统数据库擅长回答这样的问题：

  • "价格等于 100 元的商品有哪些？"
  • "用户 ID 是 12345 的订单状态是什么？"

但现实中的很多数据是非结构化的：一段文字、一张图片、一段音频。我们想问的是：

  • "和这张图长得像的商品有哪些？"
  • "和这个问题语义相关的文档有哪些？"
  • "和用户兴趣最接近的内容有哪些？"

向量数据库就是用来解决这类"相似性搜索"问题的数据库。Milvus 是其中最流行的开源实现之一。

一句话：关系型数据库回答"等不等于"，向量数据库回答"像不像"。

1.2 什么是向量？

向量就是一串数字。你可以把它想象成空间中的一个点：

  • 2 维向量：平面上的一个点 [x, y]
  • 3 维向量：空间中的一个点 [x, y, z]
  • 128 / 512 / 1536 维向量：高维空间中的点（虽然画不出来，但数学上一样处理）

在向量数据库里，我们关心的是两个向量之间的距离或相似度。距离越小（或相似度越高），代表它们越"像"。

1.3 什么是 Embedding？

Embedding是把真实世界的东西（文字、图片、声音）转换成向量的过程。

例子：

  • 文本：用 BERT、OpenAI Embedding 等模型，把一句话变成 1536 维向量
  • 图像：用 ResNet、CLIP 等模型，把一张图变成 512 维向量
  • 音频：用音频模型，把一段声音变成向量

好的 embedding 模型有个特点：语义相近的东西，向量也更接近。比如"猫"和"kitten"的向量会比"猫"和"汽车"更接近。

1.4 这个想法是怎么来的？

用向量来计算"像不像"，本质上经历了三步：

第一步：把"像不像"变成可计算的问题

人对"像不像"的判断很直观：两首歌旋律像、两句话意思像、两张图内容像。但机器不会"感觉"，它只会算数字。所以研究者首先要解决的问题是：能不能把"像不像"变成一个可计算的东西？

第二步：借几何里的距离

几百年前的数学已经有一个现成工具：空间中的点。平面上的两个点，可以用距离衡量远近。距离近 = "像"，距离远 = "不像"。

于是自然产生一个联想：如果能把一首歌、一句话、一张图也表示成空间中的一个点，那"像不像"不就变成"距离近不近"了吗？

第三步：用向量表示特征

一个东西可以拆成很多特征，每个特征用一个数字表示。比如水果可以表示为：

水果 = [甜度, 酸度, 大小, 颜色亮度]

如果两个水果的甜度、酸度、大小都很接近，它们在向量空间里就离得近，我们就说它们"像"。

现代革命：神经网络自动学向量

早期是人类手动设计特征（比如自己定义甜度、酸度）。后来深度学习发现：神经网络可以自己学出更好的向量。

比如 2013 年的 Word2Vec 发现，把词变成向量后：

  • "国王" - "男人" + "女人" ≈ "女王"
  • 语义相近的词在向量空间里确实聚在了一起

这就证明了：向量不仅能表示"像不像"，还能捕捉深层的语义关系。

一句话总结：用向量算"像不像"，本质上是把人类直觉的"相似"转化成了数学可计算的"距离"；而深度学习让这种表示从手工特征进化到了自动学习。

第 2 章：相似度度量

2.1 如何比较两个向量？

向量数据库的核心问题是：给定一个查询向量，从数据库里找到和它最相似的向量。

"相似"有很多种定义方式，Milvus 主要支持三种：

余弦相似度 Cosine

看两个向量之间的夹角。

夹角越小，相似度越高。对向量长度不敏感。

适合：文本语义相似度、主题匹配。

欧氏距离 Euclidean（L2）

看两个向量终点之间的直线距离。

距离越小越相似。对绝对大小敏感。

适合：对数值大小敏感的场景，如位置、特征强度。

内积 Inner Product（IP）

两个向量对应位置相乘再相加。

值越大越相似。同时受方向和长度影响。

适合：推荐系统，能同时反映兴趣和热度。

2.2 三种度量分别适合什么场景？

三个度量的核心区别在于：它们对"向量长度"和"向量方向"的敏感程度不同。

📐Cosine：只看方向，不看长度

cosine(A, B) = (A·B) / (||A|| × ||B||)

归一化后长度被消掉，只保留夹角。

为什么适合文本？ 文本 embedding 模型（BERT、OpenAI Embedding）通常把语义相似的句子映射到相近的方向。比如"我今天很开心"和"今天心情很好"用词不同，但意思接近，方向接近，余弦相似度就高。

文本向量的长度往往和句子长度、词频有关，而不是语义。我们看的是"意思像不像"，不是"句子长不长"。

📏Euclidean（L2）：看直线距离，长度有意义

L2(A, B) = √((A₁-B₁)² + (A₂-B₂)² + ...)

为什么适合位置、特征强度？ 当向量的"长度"本身就有意义时，L2 更合适。

比如推荐餐厅：餐厅 = [人均消费, 评分, 距离我当前位置]

  • 餐厅 A：[100, 4.5, 0.5]
  • 餐厅 B：[300, 4.6, 5.0]

A 和 B 方向可能接近，但人均消费和实际距离差很多。"离我 0.5 公里"和"离我 5 公里"的体验差异很大，L2 能反映这种绝对差异。

再比如图像亮度：两张图都是橙色调，但一张亮、一张暗。Cosine 会认为很像，L2 会认为很远。如果你想找"亮度也接近"的图片，L2 更合适。

🔥Inner Product（IP）：方向 × 长度，适合推荐

IP(A, B) = A·B = ||A|| × ||B|| × cos(θ)

为什么适合推荐系统？ 推荐场景里，"长度"往往代表"强度"或"热度"：

  • 用户兴趣向量长 → 对这个品类越感兴趣
  • 物品热度向量长 → 这个物品越热门/受欢迎

比如电影推荐：用户 = [喜剧喜好, 动作喜好, 爱情喜好]

  • 用户 A 很喜欢喜剧：[10, 1, 1]
  • 用户 B 一般喜欢喜剧：[1, 0.1, 0.1]
  • 电影《喜剧之王》=[9, 0, 1]

用 IP 计算：A·电影 = 91，B·电影 = 9.1。IP 自然地把"兴趣强"的用户和"热门喜剧"匹配在一起。如果用 Cosine，A 和 B 对这部电影的相似度可能差不多，但推荐系统更想把热门内容推给高兴趣用户。

一句话对比：Cosine 看方向，适合语义；L2 看绝对距离，适合位置/强度；IP 看方向 × 长度，适合推荐（兴趣和热度）。

2.3 归一化的影响

如果向量已经归一化（长度为 1），那么余弦相似度和内积在数学上是等价的：

cosine(a, b) = dot(a, b) / (||a|| * ||b||)
如果 ||a|| = ||b|| = 1，则 cosine(a, b) = dot(a, b) = IP(a, b)

这就是为什么很多文本 embedding 模型输出已经归一化，用 cosine 和 IP 结果一样。

  1. Cosine：看方向，适合语义相似度
  2. Euclidean：看直线距离，适合对大小敏感的场景
  3. IP：内积，受方向和长度共同影响

第 3 章：ANN 与索引

3.1 暴力搜索的问题

假设你有 1000 万个 128 维向量，每次查询都要和这 1000 万个向量逐一算距离：

1000 万 × 128 次运算 = 12.8 亿次运算/查询

这还没考虑磁盘 IO。如果每秒有几百次查询，系统根本扛不住。

3.2 ANN：用少量精度换速度

ANN（Approximate Nearest Neighbor，近似最近邻）的思想是：不要找绝对最近的，而是找一个足够近的结果，同时速度大幅提升。

衡量 ANN 效果的两个关键指标：

  • Recall（召回率）：返回的结果中有多少是真正的最近邻
  • Latency（延迟）：每次查询耗时多久

3.3 常见索引类型

FLAT / Brute Force

原理：暴力扫描所有向量。

优点：结果 100% 精确。

缺点：数据量大时极慢。

适合：数据量小（< 10 万）或对精度要求极高的场景。

IVF_FLAT / IVF_SQ8

原理：先把向量聚类成若干桶，查询时只搜索最近的几个桶。

优点：速度比 FLAT 快很多，参数可控。

缺点：需要调 nlist/nprobe，桶内还是暴力比较。

适合：中等规模数据，预算有限。

HNSW

原理：构建多层图结构，查询时从顶层贪心下降到最近邻。

优点：搜索速度快，召回率高。

缺点：建索引慢，内存占用大。

适合：高并发在线服务。

概念检查

  1. ANN：近似最近邻，用少量精度损失换取大幅速度提升
  2. FLAT：精确但慢，适合小数据量
  3. IVF：聚类分桶，查询只搜部分桶，速度较快
  4. HNSW：多层图索引，搜索快但内存占用大

第 4 章：Milvus 核心概念

4.1 从关系数据库类比

关系数据库 Milvus
数据库 Database Cluster / Milvus 实例
表 Table Collection
行 Row Entity
列 Column Field
表结构 Schema Schema
索引 Index Index（向量索引 + 标量索引）

4.2 核心概念解释

  • Collection（集合）：数据的逻辑容器，类似一张表。
  • Entity（实体）：Collection 中的一条记录，包含多个 Field。
  • Field（字段）：Entity 的一个属性，比如主键、向量、标量标签。
  • Schema（模式）：定义 Collection 有哪些 Field、什么类型、是否为主键。
  • Partition（分区）：Collection 内的逻辑分片，常用于按时间/业务维度切分数据。
  • Index（索引）：加速向量搜索的数据结构，如 IVF_FLAT、HNSW。
  • Metric Type（度量类型）：搜索时使用的距离/相似度，如 COSINE、L2、IP。

  2. Entity 类似行，是一条完整记录

第 5 章：数据建模与写入

5.1 Schema 设计

设计 Milvus Collection 时，通常需要这几类字段：

  • 主键字段：唯一标识每个 entity，通常是 INT64 或 VARCHAR
  • 向量字段：FLOAT_VECTOR 或 BINARY_VECTOR，维度由 embedding 模型决定
  • 标量字段：用于过滤和展示，如类别、时间、状态等

一个典型的文档检索 Collection Schema：

{
  "fields": [
    { "name": "id", "type": "INT64", "is_primary": true, "auto_id": true },
    { "name": "doc_id", "type": "VARCHAR", "max_length": 64 },
    { "name": "content", "type": "VARCHAR", "max_length": 65535 },
    { "name": "category", "type": "VARCHAR", "max_length": 32 },
    { "name": "embedding", "type": "FLOAT_VECTOR", "dim": 1536 }
  ]
}

5.2 写入数据

写入数据的基本流程：

  1. 连接 Milvus
  2. 创建 Collection（如果还没有）
  3. 创建 Index（针对向量字段）
  4. 加载 Collection
  5. 插入数据

注意：向量字段的维度在创建 Collection 时就确定了，之后不能修改。如果换了 embedding 模型，通常需要重新建表。

概念检查

  1. Schema 必须包含主键和向量字段
  2. 向量维度由 embedding 模型决定，创建后不可改
  3. 标量字段可用于过滤和展示
  4. 写入前通常要先创建索引并加载 Collection

第 6 章：搜索与查询

6.1 search()：向量相似度搜索

search() 是 Milvus 最核心的 API：给定一个或多个查询向量，返回最相似的 top-k 个结果。

results = collection.search(
    data=[query_embedding],
    anns_field="embedding",
    param={"metric_type": "COSINE", "params": {"nprobe": 10}},
    limit=5,
    expr="category == 'tech'",
    output_fields=["content"]
)

参数说明：

  • data：查询向量列表
  • anns_field：要搜索的向量字段名
  • param：索引搜索参数，如 nprobe、ef
  • limit：返回结果数量（top-k）
  • expr：标量过滤条件
  • output_fields：返回的附加字段

6.2 query()：标量过滤查询

query() 用于根据标量条件精确查询，不走向量索引：

results = collection.query(
    expr="category == 'tech' and create_time > 1700000000",
    output_fields=["id", "content"]
)

6.3 混合搜索

混合搜索 = 向量相似度搜索 + 标量过滤。先按向量召回一批候选，再用 expr 过滤掉不符合标量条件的，最后返回结果。

  1. search() 基于向量做近似最近邻搜索

  4. expr 可以在向量搜索时附加标量过滤条件

第 7 章：部署与生态

7.1 Standalone vs Cluster

Standalone

单节点部署，所有组件跑在一台机器上。

  • 部署简单
  • 适合开发、测试、小规模应用
  • 横向扩展能力有限

Cluster

分布式部署，角色分离。

  • 可水平扩展
  • 适合大规模生产环境
  • 运维复杂度更高

7.2 核心组件

  • Milvus：核心数据库服务
  • etcd：元数据存储
  • MinIO / S3：对象存储，持久化数据
  • Pulsar / Kafka：Cluster 模式下的消息队列（可选）

7.3 生态工具

  • PyMilvus / GoMilvus / Node.js SDK：各语言客户端
  • Attu：图形化管理界面
  • Zilliz Cloud：Milvus 的全托管云服务
  • Milvus CLI：命令行工具

快速开始：用 Docker Compose 启动 Milvus Standalone 是最常见的本地体验方式。

概念检查

  1. Standalone 适合开发和中小规模
  2. Cluster 适合大规模分布式生产环境
  3. etcd 存元数据，MinIO/S3 存实际数据
  4. Attu 是 Milvus 的 GUI 管理工具

总结与延伸

Milvus 完整流程

原始数据 → Embedding 模型 → Milvus 写入 → 建索引 → 向量搜索 → 业务应用
1️⃣数据准备

把文本、图像、音频等非结构化数据通过模型转成向量。

2️⃣Schema 设计

设计 Collection，包含主键、向量字段、标量字段，指定维度和 metric type。

3️⃣写入与索引

插入数据，为向量字段创建索引（FLAT/IVF/HNSW），加载 Collection。

4️⃣搜索查询

用 search() 做向量相似度搜索，用 query() 做标量过滤，两者结合做混合搜索。

5️⃣业务集成

把搜索结果交给下游应用，如 RAG 上下文、推荐列表、以图搜图结果。

核心要点回顾

1. Embedding

把非结构化数据转成向量，让机器能"比较像不像"。

2. ANN 索引

用 FLAT、IVF、HNSW 等索引在海量向量中快速找最近邻。

3. 混合搜索

向量相似度 + 标量过滤，满足复杂业务查询需求。

延伸学习路径

  • Embedding 模型：BERT、OpenAI Embedding、CLIP、Sentence-BERT
  • 向量检索算法：HNSW、IVF、PQ、ScaNN
  • RAG 架构：LangChain、LlamaIndex、文档分块策略
  • Milvus 生态：Attu、Zilliz Cloud、Milvus Operator on Kubernetes

一句话总结：Milvus 让"像不像"的模糊问题变成了可以高效计算和检索的工程问题，是连接 AI embedding 与业务应用的桥梁。
